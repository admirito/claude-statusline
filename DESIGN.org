#+TITLE: Design notes
#+OPTIONS: toc:2 num:nil

Why the line looks the way it does. Every display decision below was made field
by field against the data Claude Code actually sends, and several fields were
examined and then deliberately left off.

* Principles

1. *Quiet by default, escalate when it matters.* A number you cannot act on is
   noise. Windows past the first appear only above 75%, the cold-cache marker
   only when the cache is cold, mode flags only when a mode is on. The one
   deliberate exception is the cache countdown, which is on the whole time the
   cache is warm: the question it answers, "can I leave my desk", is asked
   while everything is healthy, and "will it still be warm when I am back"
   needs the number at 45 minutes as much as at 5.
2. *One fact in one place.* The context window size sits beside the token count
   it scales, not also in the model badge. Lines changed sits beside the branch,
   because both describe the working tree.
3. *Absence is not zero.* Several fields are omitted from the payload rather
   than sent as zero, and rendering a confident =0%= for "not known yet" is worse
   than rendering nothing.
4. *Muted constants, coloured variables.* The =⧗= icon and a pull request number
   never change; the percentage and the review state do. Only the second kind
   takes colour.

* Fields shown

** Rate limits

The payload carries a 5-hour window and a weekly window for Claude.ai
subscribers, each with a used percentage and the instant it resets. Behind a
gateway it may also carry a spend limit.

The 5-hour window is always shown, *with its reset countdown*, because the
percentage is not interpretable without it: 24% burned with four hours left and
24% with twenty minutes left are opposite situations, and only the second means
you can spend freely. The countdown gains minute resolution past 50%, where
"coffee or lunch" becomes a real question; below an hour it is minutes anyway.

Other windows appear only past 75% and stay coarse. Three days versus three days
and four hours changes nothing you would do.

** Pace

=»68%= is the weekly percentage the session would reach *by the reset* if it
carried on at the average rate kept since the week began. The payload gives the
instant the weekly window resets, and the window is a week long, so the week's
start is known and the figure needs no history: it is the used percentage
divided by the fraction of the week already gone.

Nothing in Claude Code shows this, and it is the only form in which a weekly
budget answers the question worth asking of it. 31% used is not interpretable:
on a Tuesday it is comfortable, on a Saturday it is not. =»54%= says the same
data as "you finish the week at 54%", and =»108%= says "you run out before the
reset".

It is always shown, unlike the other limit cells, because the answer matters
most while it is still good news. Colour is the only thing that escalates: gray
while the projection lands under 100 less the buffer, sharp yellow once it does
not, red past =PACE_RED=. The buffer is 1 by default, so the cell stays quiet
until the projection genuinely overruns; raising it warns earlier.

Two absences. The cell goes with the weekly window itself, which is missing for
API-key, Bedrock and Vertex sessions and before the first API response. And it
stays absent through the first day of the week, where the divisor is small
enough to make the answer meaningless rather than alarming: 5% used two hours in
projects to 400%.

The figure is an average over the whole week so far, which makes it stable: a
quiet weekend pulls it down slowly and a heavy Monday pushes it up slowly. That
is right for a weekly budget and wrong for a burst, which is what the 5-hour
window is for.

Colour bands: below 50 gray, 50–75 white, then yellow, orange and red at 75, 85
and 95. Percentages arrive as floats and are rounded.

The whole segment disappears when the field is absent, which is every session
before its first API response, and always on API-key, Bedrock and Vertex auth.

Past 100, a brief on the second line spells the pace out while the week has
yet to run dry: the instant it will, how long before the reset that is, and
=15→12%/day=, the daily rate kept so far against the one that would last to
the reset. The first is what the pace projects over seven days; the second is
the share left over the days left, rounded down, since a budget must not
promise more than is there, and the pair is left out when the two are equal.
The gap and the rate kept take the pace's colour, the rate that lasts is
green. The one brief that does not already show when the week resets names
it, =15h before Thu 09:00=; the others say =15h early=. A render with two
briefs gives the pace once. It turns a warning into a budget.

** Context window

Two numbers and a bar. The token count is input only: prompt tokens plus both
cache counters, matching how Claude Code computes its own percentage.

The percentage is *not* the raw fraction of the window. Compaction fires a fixed
number of tokens below the end of the window, not at a fixed fraction of it, so
the reserve is subtracted as a constant. This matters: a divisor tuned on a 200K
window overstates usage on a 1M window by about a third, because the reserve is
roughly a fifth of the small window and a twentieth of the large one. The
reserve differs slightly depending on whether auto-compact is enabled, since a
hard block sits closer to the end than the compaction trigger does.

=autoCompactEnabled= is resolved the way Claude Code resolves it: any settings
file that defines it wins in precedence order, otherwise the legacy value in
=~/.claude.json=, otherwise enabled. The =DISABLE_AUTO_COMPACT= and
=DISABLE_COMPACT= environment variables force it off.

Both token figures use one formatter that picks its unit from the magnitude, so
=1000000= renders =1M= rather than =1000K= and a future window size stays correct.

** Prompt cache

The cache cell is =⚡= hit ratio, then either the countdown or the cold marker,
then misses.

=hit_ratio= counts cache reads against *all* input tokens for the session,
uncached input included. That is a lower and more honest number than a
per-request ratio of reads to writes, which flatters itself by leaving uncached
input out of the denominator and reads =N/A= until the first cache write.

*The countdown* =⏱53m= is shown the whole time the cache is warm. Two or three
characters always: minutes rounded up to 99, then hours, so the last minute
reads =1m= rather than =0m= and no future TTL widens the cell. Its colour is the
share of the TTL already spent, using the rate-limit bands so the line has one
colour language: gray under half, white to three quarters, then yellow, orange
and red at 75, 85 and 95 percent. On a one-hour TTL those are 30, 15, 9 and 3
minutes left. Scaling by the TTL rather than by minutes left matters because
the TTL is not always an hour: subscribers on allowlisted models get =1h=, API
keys and most Bedrock and Vertex sessions get =5m=, and a fixed fifteen-minute
alarm would have been lit for the whole life of a five-minute cache.

=❄= replaces the countdown when the cache is cold, with the number of tokens the
next request re-caches. This is the one figure on the line denominated in
money. An absent =prompt_cache= object is *unknown*, not cold, and must not
render =❄=.

*Misses* =✗4·tools,rewind= are a receipt, not an alarm: by the time one shows,
the rebuild it reports has already been paid for. So nothing about it is red.
The count is permanent for the session and is the same figure =/cost= shows,
which includes rebuilds caused by idling past the TTL; those are counted here
too, as =idle=, rather than filtered out, so the two numbers never disagree.

Claude Code diagnoses each miss by comparing the request with the previous one
and names the cause: tool definitions changed, system prompt changed, model,
effort or fast mode switched, earlier messages rewritten, idle past the TTL,
nothing changed (so the server dropped it), or undiagnosed. Each becomes one
plain word rather than a glyph, because nine glyphs is a legend nobody keeps in
their head and a word needs none. A single miss can carry several causes
(=/model= usually reports model and effort together); they join with =+=. The
rare causes share =other=.

Each cause word lives for five minutes and then drops off; a diagnosis is only
interesting while you can still remember what you were doing. There is one
colour and one rule: count and words are yellow for exactly as long as a word is
on the line, and the bare count is gray. Two colours for two ages was
considered and rejected as a distinction nobody would read. The payload carries
the cause of the *last* miss only, so to show the last five minutes of them the
script records each one in the session state file, described under Cost.
Adjacent repeats collapse to
=tools×2=, which is what an MCP server reconnecting in a loop looks like.

Statistics cover the main conversation only; subagent requests are excluded.

** Effort and fast mode

Shape carries the effort level, colour carries fast mode. Two orthogonal facts
in one cell at no width cost. Rendering only the true state of fast mode also
sidesteps an ambiguity: a false value conflates "off", "this model has no fast
mode" and "temporarily unavailable".

The effort field is absent for models with no effort control, which is not the
same as unknown, so it renders =∅= rather than a level.

** Branch, worktree, pull request

Long branch names are degraded in the order of how little the dropped part is
worth: kept whole if they fit, otherwise each prefix segment is abbreviated to
one character, otherwise the tail is cut. =feature/PAY-4821-idempotent-refunds=
becomes =f/PAY-4821-idem…=.

A Claude worktree session checks out a branch named after the worktree with a
prefix; the short name from the payload says the same thing in seven fewer
columns. A plain linked git worktree gets a different glyph, because it is a
different situation.

The branch turns orange when the working directory has left the project
directory, since the branch shown then describes a repository the session does
not think it is in.

Pull request state uses a glyph rather than a word, and only the glyph is
coloured. GitLab merge requests are written =!123=, which is that platform's own
convention, not =#123=.

** Modes cluster

Output style, vim mode, agent, remote attachment and extra directories are all
non-default session states, all absent by default, and all rendered in one
colour so five columns do not become five hues. Built-in output styles get a
dedicated glyph; a custom style falls back to its initial, so a style invented
later still renders sensibly.

* The second line

A second row, for one minute at a time, and absent the rest of the day. It
carries what is otherwise invisible until it bites: the weekly window below the
75% at which line 1 starts showing it, the reset instants as clock times rather
than durations, and the detail behind a cache miss. Everything on it is either
absent from line 1 or too long to live there.

The row is not printed at all when no brief is live. An always-present row costs
a line of terminal for the whole session in order to carry a blank most of the
day, and a status line that wants two rows should earn the second one each time.

Four moments, chosen because each is one where something changed *and* you are
demonstrably at the keyboard:

1. *The first render that has rate limits.* Where both windows stand, when they
   reset, the pace, and the cache TTL. The facts you would otherwise run =/usage=
   for. Whether this has been shown is recorded explicitly, rather than
   inferred from the state file existing: Claude Code renders once at session
   start, /before/ the first API response, and that render has no rate limits
   but does write state. Inferring it meant the brief counted as already shown
   by the time the limits it reports arrived, so it never appeared at all.
2. *A new prompt after ten minutes away.* How long you were gone, whether the
   cache survived it and what the next request re-caches if not, and where the
   windows stand now. This is the one exception to "transient only": it is still
   transient, but it is timed to the moment you come back rather than to the
   moment something happened, because a notice that fires while you are away has
   already failed.
3. *A window crossing a band*, upward only: every 10 up to 50, then every 5.
   Never on a session's first render, where there is no previous band to have
   crossed from and the opening brief has just said where both windows stand. A
   weekly crossing carries the pace, since a weekly percentage without it is not
   yet a question.

   What is remembered per window is the band last *announced*, not the band it
   is in. Two bugs live in that distinction. These are rolling windows:
   =used_percentage= falls as old usage ages out, so remembering the current
   band announces the same crossing again every time the figure dips under a
   boundary and climbs back over it, which a busy five-hour window does
   repeatedly. And a crossing that happens while an earlier brief still holds
   the row is not printed, so advancing the mark on that render would lose it
   for good; it is announced on the first render after the row frees up.

   A window the state file has not seen before, because it has just rolled
   over or because rate limits have only now appeared, is /seeded/ at its
   current band rather than reset to zero. Zero would read as a crossing of
   every band below wherever the window already stands, and announce "12%" the
   moment a new five-hour window opens.
4. *A cache miss*, with the detail the one-word cause on line 1 cannot carry:
   how many tools were added and removed, how far the system prompt moved, and
   the tokens that miss re-cached.

Two briefs at once join with a dot; a third is dropped, because two at once is a
busy moment and three is a report. They are ordered news first, so a miss keeps
its slot against a crossing.

A brief is composed on the render that earns it and then kept verbatim in the
state file until it expires. "back after 47m" must not re-count itself every
thirty seconds, and the alternative, regenerating from a token, would have to
re-derive facts that have since moved on.

Claude Code updating underneath the session was considered and dropped: it
announces that itself, and a second notice is noise.

* Agent rows

Claude Code lists background agents in a panel under the prompt and can hand
each row to a command, the =subagentStatusLine=, which it runs every few
seconds with all the agents at once. This script is that command as well: a
payload with a =tasks= array is answered with one row per agent, and the main
line never runs. It is one script rather than two because a row is meant to
read as a small copy of the main line, and sharing the palette, the glyphs and
the number formats makes that true by construction rather than by care.

** What the payload does not say

The payload knows an agent's model, status, token count, context window, start
time, description and, when Claude gave it one, its name. Everything else on a
row comes from two files Claude Code keeps beside the session transcript for
each agent: a small metadata file (type, parent, nesting depth) and the agent's
own transcript (tool calls, token usage, cache writes, the background commands
it started). Neither is a published interface, both are read defensively, and
every cell they feed is absent when they are.

A transcript can be long and grows while it is read, so it is read
incrementally: only the bytes added since the previous run, and only whole
lines, since Claude Code may be mid-write at the end. The new bytes are copied
out first, so their size, their partial tail and what gets parsed are one
snapshot. A response split across several entries repeats its usage, so each
request is counted once. What the transcript has said so far is kept per agent
in a state file beside the main line's, which also holds what no single run can
know: when the current status began, when the tokens last grew, and their
recent history.

** Layout

Every cell has a fixed width, so the rows read as a table and nothing jumps
between ticks. The exceptions are the identity bracket, padded to the widest
bracket in the panel, which moves only when an agent arrives or leaves, and
the context column, which widens by a few columns while a fork's longer cell
is on screen. Nested
rows get a tree connector from Claude Code, two columns per level, drawn in
front of the row's text; the bracket's padding gives those columns back, so
every column after it still lines up with the rows above.

Whatever varies in width goes after the =│=, in the label area, where a count
appearing or growing moves nothing else: the marks, then the task, then the
newest tool call.

** Identity

The bracket is the main line's badge, model then effort glyph, and each part is
gray where it is the same as the main session's and in the main line's own
colour where it differs, so what stands out is exactly what is different. An
agent that sets no effort inherits the session's, so its glyph is always gray.
The main session's model and effort come from the main line's state file, which
records them for this; without it, nothing is claimed to match.

The agent type follows, except =general-purpose=, the default, which is absent
as the main line's defaults are. A custom type is shown in the colour its
definition gives it. Claude Code keys colours by type, never by name, and the
metadata file does not record them, so the colour is read from the definition
itself: the project's =.claude/agents/= before the user's, matched on the
frontmatter =name=, since file names need not match. A name, when Claude gave
the agent one, is a different thing and goes elsewhere: =@name=, in the label
area, because a name is what =SendMessage= addresses.

A fork is marked =⋔fork=, in a pink nothing else on either line uses, because
whether an agent started fresh or with a copy of the whole conversation changes
everything about its context. =⑂= would have been the obvious glyph, but the
main line already uses it for a linked git worktree.

** Activity and state

The activity slot is ten columns, always. While tokens flow it is a sparkline,
one bar per thirty seconds of growth, scaled to the largest step, with bars not
seen yet drawn flat so that the cell never grows. Claude Code runs the command
every five seconds, and a bar per run made the line crawl without pause; a bar
per thirty seconds moves it at most twice a minute, and ten of them cover five
minutes, the agent's rhythm rather than its last few breaths. A new agent's
line starts flat and fills in bar by bar. The script keeps that history itself
rather than taking the payload's own samples, which restart from a single
sample whenever Claude Code redraws the panel.

When tokens stop, the slot says why instead, and for how long:

- *Quiet*, =▁▁▁▁▁▁▁ 2m=: running, but no new token for thirty seconds or more.
  Something inside one step is taking long: a command, a slow response, or an
  unanswered permission prompt. The time turns yellow past a minute and orange
  past five, so a stuck agent stands out.
- *Waiting*, =⧖ wait 10m=: the status is =completed= but the row is still in
  the panel. The panel hides agents that are done, so a completed row on screen
  is one kept alive by background work of its own, a command it started or
  agents of its own, and it wakes when that work finishes.
- =✗ failed= in red, =⚠ stopped= in orange, =◌ queued= and =⏸ paused= in gray.

Both times count from the first run that saw the state: a lower bound, never an
overstatement.

The newest tool call follows the task in every state, =· Bash go test=, so it
neither flickers in and out between calls nor vanishes when the agent stops. A
quiet agent's tool is what it is stuck in; a waiting agent's is usually what it
is waiting for.

** Cost, context and cache

Cost is estimated the way Claude Code estimates the session's: the transcript's
tokens at list price, or at the rates in a =modelPricing= table, which Claude
Code honours only from managed settings, so the script reads it only from
there. It is an estimate at API rates, like the main line's, not what a
subscription is charged.

The context cell uses the main line's formula, a share of the room before
auto-compaction, so the same percentage means the same thing on both lines. A
fork shows what it inherited and what it has added, =⋔366+5K=, the inherited
part taken from its first request. A fork's context can later fall below what
it inherited, when old tool results are cleared from it on waking; it then
shows its total alone.

The cache cell speaks the main line's language too, with two changes. A
healthy hit ratio, 75% or more, is the least interesting number on the row, so
it is left out and the cell is the countdown alone, =⚡5m=. And a cold cache
moves its =❄= to the context cell, =❄143K·14%=, because what waking the agent
rebuilds is that context; the cache cell keeps the ratio it had, =⚡❄44%=.
Agents get a five-minute cache unless configured otherwise, so a waiting
agent's cache usually goes cold long before it wakes.

** The marks

After the =│=, each only when it applies: output past 10K, =↗48K=;
compactions, =⟲2=; the agents nested below, =+3=; its own background commands
still running, =&2=; its worktree and pull request; its name; failed tool
calls, =✗2=.

=+N= counts every agent below, at any depth, because the panel lists nested
agents only once their parent is opened, and a problem three levels down is
otherwise invisible. It carries the worst state below it: =✗= one failed or
was stopped, =▁= one has been quiet for five minutes, =❄= one waits with a cold
cache. Claude Code's own row has a descendant count, but a replaced row loses
it, so it is rebuilt from the parent links in the metadata.

=&= is the shell's background operator, and =$= would have read as money next
to the cost.

** Worktrees

An agent can run in a git worktree of its own. Claude Code creates it under
=.claude/worktrees/= on a generated branch, and by default starts it from the
remote's default branch rather than from yours, so an agent sent to fix
something while you are on a feature branch works on code without your branch
in it. The mark says what matters without repeating the main line:

- =⎇+12/-3=: what it changed there, untracked files counted as added lines,
  as a new file counts in a diff. Only the first 4 MB of untracked files is
  read, since this runs every few seconds and a build can leave anything
  lying around.
- =↑2=: its own commits, which a diff would not show.
- A name only when it says something: the agent's own branch if it moved to
  one, =⎇fix/parser=; otherwise, in orange, where it started, and only when
  your HEAD is not in it, =⎇main=. A worktree started from wherever HEAD was
  is named by a branch holding that commit, yours first, =⎇main~1=.

Its pull request, once the branch exists on =origin=, is the main line's PR
cell, =#142⋯=. Looking it up is a network call, the only one the script makes,
so it never runs in the foreground: a detached =gh= refreshes it at most once
a minute per branch, the row shows what the last lookup found, and a lookup
that fails keeps it rather than blanking it.

** Cost of a run

One =jq= pass over the payload and one over the settings, then per agent: a
=jq= pass over the transcript's new bytes when there are any, one over the
metadata file the first time the agent is seen, and for an agent in a worktree
a handful of =git= calls. A worktree's starting point and a type's colour never
change, and are looked up once.

* Fields deliberately not shown

| Field                  | Why not                                                       |
|------------------------+---------------------------------------------------------------|
| =thinking.enabled=      | On models where effort and thinking are coupled it is constant, and where it would differ the effort glyph already shows it |
| =exceeds_200k_tokens=   | Exactly derivable from the token count already displayed       |
| =version=               | Static for the session, and there is no update-available signal to make it actionable |
| =session_name=          | Unbounded width in a line kept narrow                          |
| =session_id=, =prompt_id= | Nothing a human acts on                                      |
| =workspace.repo=        | Restates what the branch and the terminal title already say    |
| =prompt_cache.requests=, =expected_rebuilds=, =cache_write_tokens=, =miss_recache_tokens= | Session history, nothing to act on; =hit_ratio= already summarises it |
| =prompt_cache.ttl=      | Used, not shown: it scales the countdown colour                |

=prompt_id= is not displayed either; it is how a render tells a new user turn
from a re-render of the same one, which is what dates the "back after" brief.

=session_id= was also considered as a cache key for the two git calls, and
rejected: git state changes without a new session, so a cached branch or dirty
flag would render a confidently wrong line, and the calls are milliseconds.

* Cost

For the main line, one =jq= pass for the payload and one for the account and
settings files, plus two =git= calls; the agent rows' own cost is under Agent
rows. The payload pass emits key/value pairs rather than a fixed
sequence, so adding a field later cannot silently shift every value after it.

One state file per session is the only thing the main line writes: the recent
cache misses, what the previous render saw (its prompt id, activity instant,
output tokens, the band last announced for each window, whether the opening
brief has been shown) and any brief still inside its minute. It is read once
at the top and written once at the end, and only when something in it changed.
Its lines are typed by their first field, so a format that grows later cannot
shift the meaning of an old line and a file from an earlier version is ignored
rather than misread.

Fields are separated by US (0x1f), not by a tab, because tab is IFS
/whitespace/: =IFS=$'\t' read= folds a run of tabs into a single delimiter, so
every field after an empty one shifts left. Three fields are routinely empty.
US is not whitespace and cannot occur in any of the values.

The directory must be the user's own, not merely writable: in a shared
=/tmp=, =mkdir -p= accepts a directory someone else created first, and the
files in it would then be read as this session's state. The agent rows check
every field they read back as well, since a number from the file reaches bash
arithmetic.

The session id is accepted as a file name only if it is made of letters,
digits, dots, underscores and dashes, and is neither =.= nor =..=, both of
which pass that test and name a directory.

A state file that cannot be kept, because the directory is unwritable or the
id was rejected, suppresses the second line altogether rather than falling
back to rendering briefs from memory. Nothing would record that a brief had
been shown, so the opening one would print on every render for the life of the
session: a permanent second row is a worse failure than a missing one.

"Activity" is the last moment the session did anything: a new prompt, or more
output tokens. Not the render clock, which ticks while idle, and not the prompt
alone, which would call a twenty-minute turn twenty minutes away from the desk.

* Bugs worth remembering

Found while building this, all of them the kind that pass a happy-path test:

1. *=false // true= in jq is =true=.* =//= is the alternative operator, not a
   null-coalesce, and it treats =false= as empty. A =last // true= default
   silently overrode an explicit =false= setting.
2. *=GIT_DIR= is git's own environment variable.* A shell variable of that name
   is read by every =git= call as the path to a =.git= directory, and if one ever
   arrives exported the branch segment reads =no-git= forever.
3. *=git branch --show-current= prints nothing on a detached HEAD*, which is the
   state during a conflicted rebase or a bisect: exactly when the branch matters
   most. Fall back to the short SHA.
4. *=printf '%.0f' abc || printf '0'= yields =00=.* Bash's printf already prints
   =0= for an unparsable value *and* returns non-zero, so the fallback corrupts
   the field it was meant to protect.
5. *=git diff-index= compares stale stat data*; =git diff --quiet HEAD --=
   refreshes the index as it goes, at the same cost. Both exit 128 outside a
   repository, so test for exit 1 specifically rather than for non-zero.
6. *Numeric parsing follows the locale.* Under a comma-decimal locale
   =printf '%.2f' 4.82= stops at the dot and yields =4.00=. Unset =LC_ALL=, which
   would mask the fix, and export =LC_NUMERIC=C=; leave string handling in the
   UTF-8 locale so =${#name}= counts characters rather than bytes.
7. *A float in =$(( ))= is a syntax error* that abandons the rest of the
   enclosing compound command, blanking part of the line rather than failing
   loudly. Floor integer fields in jq.
8. *=jq -s= indexes by position*, so a missing file shifts every later file up
   and silently disables whatever depended on the last one. Select by shape.
9. *A status line must exit 0.* Claude Code discards the output of a command
   that fails, so a non-zero exit blanks the whole bar until the next render.
   The trap is =[ -n "$x" ] && cmd=, whose status is false whenever =$x= is
   empty: harmless in the middle of a script, fatal as the last command. v6
   ended the state file with an optional brief line written exactly that way,
   and briefs are absent on most renders, so the bar blanked constantly while
   streaming. v5 had the same shape but wrote the file only on a cache miss,
   which is why it went unnoticed. Every such line is an =if= now, and the
   script ends with an explicit =exit 0=.
10. *Tab is IFS whitespace.* =IFS=$'\t' read -r a b c= folds a run of tabs
    into one delimiter, so a record with an empty field is read back with
    every later field shifted left. It is invisible until a field is empty,
    which for the state file meant the first render of every session: an
    activity timestamp landed in =prompt_id=, a zero landed in =activity=, and
    the line greeted the first prompt with "back after 20723d". Separate
    fields with a character that is not whitespace.
11. *bash 3.2 evaluates a subscript that =||= should have short-circuited.*
    =(( n == 0 || x > arr[n-1] ))= returns the right answer and also prints
    "bad array subscript" to stderr, once per render, on every macOS session
    whose array happens to be empty. Read the element into a scalar first.
12. *jq builds its output in one pass.* One payload field of an unexpected
    type, reaching =floor=, fails the whole program, and every field goes with
    it: the line renders as though stdin had been empty. Test =type== rather
    than trusting the schema.
13. *A truncating redirect is not atomic.* Claude Code kills a status line
    still running when the next update arrives. =… > "$f"= killed halfway
    leaves a half-written file for the next render to read; write to
    =$f.$$= and =mv= it into place instead.
14. *=${x^}= and =${x,,}= are bash 4.* They fail at runtime, not at parse time, so
   an untested branch carrying one looks fine until the day it runs. macOS ships
   bash 3.2.
15. *A comma binds tighter than you think in jq.* =A | f, B= is =A | (f, B)=,
    so =B= runs on the output of =A= rather than on the input. The agent
    payload's header and its rows were first written that way, and every row
    read =.tasks= from an array, failed, and the panel stayed as it was.
16. *=\u= is not a regex escape in jq.* A character class written
    ="[\\u0000-\\u001f]"= is a class of the letter =u= and some digits, and
    replacing it blanked most letters out of every label. Map control
    characters by code point with =explode= and =implode= instead.
17. *=git ls-files= prints paths relative to where git ran.* Piped into =xargs
    cat= from anywhere else, every file is missing, silently, and a worktree's
    new files counted as nothing.
18. *A status can have two meanings.* An agent reported =completed= is either
    done or waiting on background work of its own, and the payload does not
    say which. The panel hides the first kind, and that is what makes the
    second readable.
19. *Bash arithmetic evaluates a variable's contents.* =(( x > n ))= with =n=
    holding =a[$(cmd)]= runs =cmd=. The agent state's history field reached
    arithmetic unchecked, so a planted state file could run a command; every
    field read back is validated now, not only the ones that looked numeric.
20. *One bad entry can freeze an incremental reader.* The transcript pass
    failed as a whole on one entry of an unexpected shape, the offset rightly
    stayed put, and so every later run failed on the same entry and the
    agent's counters stopped for good. Each entry is folded in inside =try=
    now, and a bad one is skipped.
21. *=label= is a jq keyword.* On jq 1.6, =… as $label= is a syntax error
    (later versions accept it), and with stderr discarded the rows simply did
    not appear.

* Known limitations

- Untracked files never earn the dirty marker; neither =git diff= nor
  =diff-index= sees them.
- The overage-included weekly window is read if it ever appears, but Claude Code
  does not currently put it in the status line payload. The slot is absent-safe
  and costs nothing.
- Several glyphs are East Asian /Ambiguous/ width: one column in a Latin-locale
  terminal, two in a CJK-configured one.
- Two misses between two renders leave only the later cause visible; the
  earlier one is journaled as =?= so the sequence keeps its length. Renders
  follow every assistant message, so this needs two misses in one turn.
- A session resumed within five minutes of a miss shows that miss's word from
  the journal beside a count that restarted with the new process.
- A band is announced once per window even if usage crosses it, falls back and
  crosses it again, which is the intended reading of "upward only" but does
  mean a genuine second climb goes unremarked.
- The pace assumes the weekly window is exactly seven days long, which is what
  its name and every observed reset say, but the payload states only when it
  ends, not when it began.
- A brief composed in one terminal is not shown in another attached to the same
  session; the state file is per session, and only one renderer reads it at a
  time in practice.
- A band is announced at most once per window, so a crossing that arrives while
  an earlier brief holds the row waits for the row rather than stacking, and a
  second climb through the same band after a dip is silent.
- State files are one per session and under a kilobyte; they die with the login
  on Linux (=XDG_RUNTIME_DIR=) and are swept by the OS on macOS, but are not
  cleaned up by the script itself.
- A live brief is stored with its colour escapes in it, so the file is not
  pleasant to =cat=. Storing it plain would mean re-rendering it against a
  palette that may have changed, for no gain.
- Agent rows: the quiet and wait times count from the first run that saw the
  state, so they start late when the panel was not being drawn.
- Agent rows: a cold fork's rebuild can be much smaller than its context, since
  its prefix is the parent conversation, whose cache may still be warm. It is
  marked cold all the same.
- Agent rows: a plugin agent's type keeps the default colour; its definition
  lives inside the plugin.
- Agent rows: the cost leaves out the data-residency and fast-mode surcharges,
  which the transcript does not record.
- Agent rows: untracked binary files in an agent's worktree count their
  newlines as lines, and only the first 4 MB of untracked files is counted.
- Agent rows: the cells are padded by character count, which is column count
  only in a UTF-8 locale; with =LANG= unset they misalign. The task and tool
  text are fitted by display width, counting CJK and emoji as two columns,
  but symbols of ambiguous width as one.

* The assumption most likely to drift

The agent rows are built mostly from files Claude Code keeps for its own use:
each agent's metadata file and transcript, where they are, and the shape of
what is in them. None of it is documented. The script reads them defensively,
and a cell whose source disappears is absent rather than wrong, but a release
that moves or reshapes them will quietly empty much of a row.


The context reserve assumes compaction fires a fixed number of tokens below the
window. That figure is not part of any published contract and was worked out by
inspection, so it can change in any release. Claude Code also has a background
pre-computation path that may begin earlier. If that path ever gates compaction itself, a large window would
compact sooner than this script predicts and the bar would overstate the
headroom. It is not detectable from the payload.
